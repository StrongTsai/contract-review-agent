# 合同审核数字员工 · 面试话术

> 用途:面试前过一遍。核心心法:**「决策 + 理由」是亮点,「TODO 无理由」是减分**。这个项目里每一个「为什么」你都能答上来,就是你的护城河。

---

## 0. 30 秒项目介绍

> 我做一个「合同审核数字员工」,用 LangGraph 搭工作流 + DeepSeek 做大脑。外层四个节点(信息抽取 → 风险审核 → 人工审批 → 报告)由我显式编排;审核节点内部是一个**自主 agent**,绑了两个检索工具,通过本地 bge 向量库查**全量《民法典》1260 条 + 判例**,自己决定查什么、查几次,再输出结构化审核结果;遇到高危风险用 `interrupt` 挂起转人工,人工决定走条件边路由。整套东西覆盖了工作流、嵌套 agent、RAG、人机协同四样,不是纯 demo。

---

## 1. 架构怎么讲(画个图讲)

```
外层(工作流,开发者决定下一步):
START → 抽取 → 审核 → 人工审批 ─(确认)→ 报告 → END
                        └──(驳回)→ END

内层(agent,模型决定下一步):
审核节点 = create_agent(model, tools=[search_law, query_case],
                        response_format=ReviewResult)

内层第二种形态 —— supervisor 多智能体(把单个 agent 拆成 4 个专家 + 1 个调度员):
START → 抽取 → supervisor ⇄ {违约金 / 责任 / 付款 / 争议 4 个专家}
                       └──(FINISH)→ 去重汇总 → 人工审批 ─(确认)→ 报告 → END
                                                          └──(驳回)→ END

内层第三种形态 —— supervisor 并行版(把「循环派工」换成 Send 一次扇出):
START → 抽取 → supervisor ─(Send 扇出)→ {4 专家并行} → 去重汇总 → 人工审批 ─(确认)→ 报告 → END
                                                                    └──(驳回)→ END
```

**一句话点破**:这是「工作流里套一个 agent」。外层是确定性编排(固定边),内层让模型自主决策(调不调工具、调几次、查什么关键词)。**判据:「下一步谁决定」**——开发者决定 = 工作流,模型决定 = agent。

## 2. 每个技术决策的「为什么」

### 2.1 为什么用 LangGraph(而不是手写 while 循环 / 纯 LangChain)
- **手写循环**:工具调用循环、断点续跑、状态管理、人工介入,全部要自己写,容易出 bug 且不可维护。
- **纯 LangChain**:偏「链式调用」,做不了「有环、有中断、有状态」的图。
- **LangGraph**:把「状态 + 节点 + 边 + checkpointer」显式建模,天然支持环(agent 循环)和中断(interrupt 转人工)。**选它是因为业务是「有环、有中断的图」,不是一条直线。**

### 2.2 为什么「工作流 + 嵌套 agent」混合形态(不是全 agent,也不是全工作流)
- **全 agent**:把「先抽取还是先审核」也交给模型,不可控、成本高、易跑偏。
- **全工作流**:审核节点只让模型「看合同直接输出」,没有查证能力,模型靠背法条(可能瞎编)。
- **混合**:需要确定性的地方(顺序、审批)用工作流;需要智能决策的地方(查什么法条)用 agent。**「该钉死的钉死,该放权的放权」**——这是生产级 agent 的主流形态,supervisor 多智能体也是同一思路的扩展。

### 2.3 为什么向量检索(而不是关键词检索)
- 关键词匹配是「字面相等」,查「违约金太高了」匹配不到写着「过分高于」的第 585 条。
- 向量检索是「语义相似」:实测查「违约金太高了」,第 588 条(违约金与定金择一)、第 591 条(违约后防止损失扩大)虽然**没有「太高」二字**,也因话题相关被命中。
- **一句话:法律条文和用户问题的用词天然对不上,必须靠语义。**

### 2.4 为什么本地 bge-small-zh-v1.5(而不是 OpenAI embedding)
- 零 API key、零成本、离线可用,中文效果好(`bge-` 系列是中文 embedding 的标杆)。
- 512 维,小而够用;1260 条 embed 完才 2.4 秒。
- **代价**:检索质量略低于大模型 embedding,但合同审核场景「法条级语义」够用。**选小模型 = 拿一点精度换零成本和隐私。**

### 2.5 为什么法条原文和裁判规则分开(不混在一起)
- 早期语料里第五百八十五条被我塞了一句「司法实践以实际损失 30% 为上限」——**那不是法条,是司法解释的实务口径**。
- 换成全量民法典后,法条库只存**权威原文**,模型引用准确;「30% 上限」「LPR 四倍」这类口径,以后单独建「裁判规则/司法解释库」。
- **理由:不同知识权威级别不同,混在一起会让模型分不清「法条」和「注释」。**

### 2.6 为什么 create_agent(而不是 create_react_agent / 手搓)
- 我一开始手搓过一遍 ReAct 循环(`bind_tools` + `ToolNode` + 条件边成环),**懂了底层**。
- 生产里用 `create_agent`(LangChain v1 官方工厂):`create_react_agent` 已弃用,`create_agent` 引入 middleware 体系、底层仍是 LangGraph。
- **一句话:底层会手写,生产用封装——面试官最喜欢这个组合。**

### 2.7 为什么 response_format(而不是循环完再调 with_structured_output)
- agent 循环里输出不固定,但外层要 `ReviewResult` 结构化对象。
- `response_format=ReviewResult` 让框架处理「循环里自由调工具,最后强制结构化」,一行搞定。
- **底层机制**:它注入一个名为 `ReviewResult` 的合成工具,模型「调用」它来吐结构化数据,框架解析成对象。对 DeepSeek 这种非原生结构化输出的模型,自动选了「函数调用模拟」策略——等价于我之前的 `with_structured_output(method="function_calling")`。

### 2.8 为什么 interrupt 转人工(而不是全自动出报告)
- 合同审核是**高风险决策**,高危条款(无限责任、畸高违约金)必须有人拍板,不能 AI 自动放行。
- `interrupt` 挂起图、`Command(resume)` 把人工决定传回来,条件边据此路由「确认 → 报告 / 驳回 → 结束」。
- **这是「人机协同」的治理点,不是技术炫技——它回答的是「AI 错了谁负责」。**

### 2.9 为什么用 OCR(而不是轻量 VLM)做「眼睛」
- 轻量 VLM(Qwen2.5-VL / MiniCPM-V)能「看 + 懂」一步到位,但它倾向**理解后转述**而非**忠实转录**——合同里「千分之五」被 VLM 换算成「0.5%」或漏一个字,就是法律事故。
- OCR 是确定性的,逐字转录、零幻觉。而「转录(写了什么)」和「推理(有没有风险)」是两件事,各选最合适的:转录用 OCR、推理用 DeepSeek。
- VLM 不是替代,是补充——以后要「识别印章/表格/手写」这类视觉理解,再上 VLM 与 OCR 并行。
- **一句话:知道什么时候用哪个,本身就是架构能力。**

## 3. 高频追问 + 答法

### 3.1 「embedding 是怎么切分的?」
- 我的语料是「一条法条 = 一个 chunk」,因为法条本身是语义原子,1~3 句,远低于 bge 的 512 token 上限,**不需要额外切分**。
- 真要面对长文档(整本合同),才需要显式 chunking,而且必须盯 512 token 的截断上限(超了会被静默丢掉)。
- chunk 大小 + 重叠是经典调参点,「按法条条目切」本身就是一种语义边界切分策略。

### 3.2 「为什么每次运行都重新加载模型?」
- 每次 `python main.py` 都是全新进程,`@cache` 只在进程内有效。
- 分两层缓存:磁盘缓存(权重只下载一次)+ 内存缓存(`@cache`,进程内复用)。加载 2.4s 是「从磁盘读进内存」,不是重新下载。
- 生产里换成 FastAPI 长驻进程,启动加载一次即可。

### 3.3 「向量相似度怎么算的?」
- `normalize_embeddings=True` 把向量归一化,这时**点积 = 余弦相似度**。
- `self.vectors @ q` 就是语料矩阵和查询向量做点积,`np.argsort(-scores)` 取 top_k。全程 numpy,没上 FAISS(规模还小,用不上)。

### 3.4 「怎么保证模型不瞎编法条?」(防幻觉)
- 三层:① 法条来自**真实检索**(不是模型记忆);② 工具返回的是**权威原文**(来源 flk.npc.gov.cn);③ LangSmith 能**回放**「模型到底查了哪几条」。
- 实测轨迹:模型先 `search_law×2` + `query_case`,再输出结论——引用的第 585 / 497 / 506 条都是检索命中的。

### 3.5 「检索不准怎么办?」
- 调 `top_k`(现在 3);引入 **rerank**(粗排向量 + 精排重排序模型);**混合检索**(向量 + 关键词/BM25 加权,法律条文有精确术语,关键词检索有独特价值)。
- 这些都还没做——我会说清楚「当前是 v1,这几点是明确的下一步」,而不是含糊。

### 3.6 「数据规模大了怎么办?」
- 现在 1260 条,numpy 点积(2.6MB 矩阵)够用;规模上万,换 **FAISS**(近似近邻),向量**持久化到磁盘**(避免每次启动重 embed)。
- 分层:小规模 numpy、中规模 FAISS、超大规模向量数据库(Milvus/Qdrant)。

### 3.7 「多用户并发怎么办?」
- 现在是 `MemorySaver`(内存 checkpoint),单机单会话;换 **Postgres/Redis checkpointer** 即多用户、跨重启持久化。
- 这是「状态外置」的问题,架构上已经留好了口子(只换 checkpointer 实现)。

### 3.8 「token 成本怎么控?」
- 已接 **LangSmith 追踪**,能按项目/会话看 token 和成本。
- 手段:`temperature=0`(审核要确定性)、`thinking` 关闭、top_k 控制检索注入量、必要时历史消息摘要。

### 3.9 「怎么扩展到多模态?」(已落地)
- 已用 **RapidOCR**(ONNX Runtime 跑 PaddleOCR 同款模型)把扫描件/图片/PDF 转文本(图片直接 OCR,PDF 先用 fitz/PyMuPDF 栅格化),再走现有四节点流程——「OCR 当眼睛 + DeepSeek 当大脑」。
- 选 RapidOCR 而非 PaddleOCR / macOS Vision:PaddleOCR 中文最强但 paddlepaddle 在 Apple Silicon 难装又重;macOS Vision 零依赖但 Mac-only、无干净 Python API;RapidOCR 一行 `uv add`、跨平台、中文同精度。
- OCR 输出有噪声(换行处数字切开、标点偶尔丢),但下游 DeepSeek 天然抗噪、能重建语义——实测 `10%` 被切两行仍被正确归一。**转录交给 OCR,理解交给 LLM,各干各擅长的。**
- 这是**异构多模型**思路——不同任务用最合适的模型,而不是指望一个大模型包打天下。

### 3.10 「同一条合同跑两遍,风险清单不一样怎么办?」(可复现性)

- **先分清两件事**:不能波动的 = 最终结论(放行 / 驳回);可以波动的 = 候选风险清单的措辞、条数、理由长短。
- **架构已兜底**:最终结论是 `interrupt` 转人工、**人拍板**的,不是模型直接放行。所以「候选措辞有波动」被隔离在人工终审之外——审核结论可复现,因为它是人确认过的。
- **三层答法**:
  1. **架构**:模型只出候选、人终审 → 结论稳定(随机性被关在人工闸门之前);
  2. **工程**:`temperature=0`(已做)+ 结构化输出约束 + self-consistency(同一条跑 3 次,取 ≥2 次都报的风险,压掉单次采样波动);
  3. **可审计**:LangSmith trace 每次可回放「专家查了哪几条法条、为什么得出这个结论」。
- **一句话**:我不回避「LLM 有随机性」这个事实,但我的架构把随机性关在人工终审之前——模型给候选、人定结论,再压候选波动、保证可审计。可解释性比字节级一致更重要。

### 3.11 「多智能体的风险清单怎么去重?」

- **去重语义先说清**:去的是「同一风险点」,不是「同一条款」。同一条款可以有多个不同风险(如「付款方式」条款同时有「验收标准缺失」和「质保金模糊」两个风险),都该保留。
- **判据两段式**:`clause` 判断「同一条款」 + `risk_type` 判断「同一风险点」,两个都命中才去重。
- **clause 为什么用子串匹配,不用 embedding 阈值**:多个专家抄同一条款,有的带「第X条」编号、有的不带,embedding 相似度被这个前缀差异拉到 0.88 以下,阈值怎么设都临界;子串匹配(去空白后 `a in b`)天然免疫「前缀/截断」差异。
- **risk_type 为什么用 embedding,不用 reason**:reason 是长文本,两条 reason 讨论同一条款时都会复述条款原文,共同词把相似度撑到 0.83,无论风险角度是否相同——**无区分度**;risk_type 是「风险类别」短标签,不含条款复述。实测同一风险点(「高额违约金」vs「违约金畸高」)0.80、不同风险点(「管辖」vs「争议解决」)0.61,阈值 0.75 干净分开。
- **宁漏勿杀**:合同审核「多留一条是烦,少留一条是事故」。判据宁可保守(漏去重),绝不误杀(删真风险)。

### 3.12 「supervisor 为什么从串行派工改成 Send 并行?」

- **串行的病根**:supervisor 每次只派一个专家,专家干完回 supervisor 再决策——4 个专家依次跑 + 4 次决策往返(每次都把全文重读一遍)。但 4 个专家审同一份合同的不同方面,彼此零依赖,串行是白排队。
- **Send 并行**:supervisor 只跑一次,一次性列出要派的专家(`experts` 列表),条件边函数返回 `[Send(专家, {...})]`,框架把状态扇出给多个节点并发执行,全部跑完汇合到 `summarize`。
- **并行让 supervisor 从「循环」变「一次决策」**:串行版 supervisor 节点跑 4 次,并行版只跑 1 次。
- **`findings` 的 `operator.add` 就是合并器**:扇出的 4 个分支各自 return 自己的 findings,框架在汇合点用 reducer 累加——当初串行时写的 reducer,现在正好当并行合并器用,不用改。
- **坑:`Send` 的 arg 是分支的完整输入,不继承父 state**。`Send(name, {})` 传空 dict,分支节点读 `contract_text` 就 KeyError;必须 `Send(name, {"contract_text": ...})` 显式带字段。
- **动态派工的边界**:当前 4 专家是固定分工,LLM 只决定「派不派」,是「半动态」;真正的动态派工是专家/工具本身动态生成(通用 agent 池),那才是 supervisor 模式的主场。

## 5. 复盘:哪些是「决策」,哪些还是「债务」

**决策(能讲出理由,加分)**:
向量 vs 关键词、本地 embedding vs OpenAI、法条原文 vs 裁判规则、工作流 + 嵌套 agent、create_agent vs 手搓、response_format 策略、interrupt 转人工、OCR vs VLM(眼睛选忠实转录)、RapidOCR vs PaddleOCR/macOS Vision。

**债务(主动承认 + 说明下一步,反而加分)**:
- 检索还没上 rerank / 混合检索 → 下一步。
- 向量没持久化(每次启动重 embed 2.4s)→ 规模上来再做。
- checkpointer 还是内存版 → 多用户换 Postgres。
- 语料来源是第三方 GitHub,未对照官方库逐条复核 → 生产前必须核验。
- OCR 还没做「版面还原」(换行处数字会切开,现在靠 LLM 归一化)→ 多栏/表格/盖章场景再做。
- PDF 走「栅格化 → OCR」,还没做「文本型 PDF 直接 `get_text()` 优先」优化 → 文本型合同 PDF 会白跑一遍 OCR,更慢。

> 面试里被问「还有什么没做」,不要慌:把债务**当成「我知道下一步是什么」的证据**来讲,而不是「我没做完」的包袱。
